# D2 Electric Nova 專項逆向分析與閉環渲染修復任務

## 一、任務目標

你現在負責修復 D2 Agent World 專案中的 **Electric Nova（電系新星）渲染問題**。

目前已經有原始資源及預處理圖集，但將動畫排列在遊戲場景中時，出現以下問題：

* 新星外擴時無法形成連續、完整的環形輪廓。
* 橢圓的頂部、底部或其他區段出現黑色間隙。
* 左右兩側的電弧可能堆疊成水平長條或毛刷形狀。
* 電弧之間的厚度不一致，呈現竹節狀，而不是連續的能量光帶。
* 半徑增大後，粒子或切片之間的距離過大，造成環形破裂。
* 不同方向的 DCC 圖元可能選錯方向，造成翻轉、旋轉錯誤或輪廓不連續。
* 使用多層光環填補間隙時，小半徑區域可能過亮、糊成白色團塊，大半徑則可能出現重影。

**最終目標：在盡可能忠實於 D2 原始技能行為、圖元、方向及動畫時序的前提下，修復新星擴散時的方向錯誤、間距不均與非預期的斷裂。**

不要一開始就增加粒子數量、放大圖片或直接疊上三層光環。先定位錯誤發生在哪個階段，再選擇最小且正確的修復方式。

## 三、第一階段：建立現況報告，不要立即修改

在修改程式碼前，完整追蹤 Electric Nova 現在的渲染流程。

至少確認：

1. 原始 DCC 是如何解碼的。
2. `electricnova.png` 是否由原始資源正確產生。
3. `electricnova.json` 的方向、影格和 Offset 是否正確。
4. 每幀的 Anchor、原始 Offset、裁切區域與 Atlas 座標如何計算。
5. 每個方向的 13 幀如何播放。
6. 新星的每個圖元如何決定世界位置、螢幕位置與旋轉方向。
7. 是否在播放時又進行一次縮放、旋轉或方向轉換。
8. 是否存在重複套用等軸測投影的問題。
9. 加法混色是否被重複套用，或在不同圖層之間產生亮度累積。
10. 環形生成與動畫播放是否被混在同一段程式碼中。

請輸出：

```text
ELECTRIC_NOVA_FORENSICS.md
```

報告要清楚區分：

* 已由程式碼或實際資源證實的事實。
* 根據畫面推測的原因。
* 尚待原廠資料或對照圖驗證的假設。
* 每個問題發生在哪個模組、函式或計算步驟。

禁止把推測直接寫成原廠機制。

## 四、第二階段：考證原廠 Nova 的實際機制

先確認 D2 原始技能與客戶端效果的關係，再決定正確的渲染模型。

需要調查：

```text
Skills.txt
Missiles.txt
相關的 DCC / COF / 動畫資料
原廠客戶端技能及飛彈處理邏輯
現有專案中對應的解析器與渲染程式
```

特別檢查目前流傳的以下說法是否有可靠依據：

* Nova 是由多個獨立飛彈或子圖元向外發射。
* Nova 存在專用的封閉圓環渲染機制。
* `dofunc` 或 `pCltDoFunc` 對應的原廠處理方式。
* 16 個 DCC 方向代表的究竟是角色／飛彈朝向、圖元朝向，還是另一種方向索引。

必須查明相關資料欄位的實際定義及執行路徑。不能因為看見某個函式編號，就直接推斷完整的渲染機制。

如果能取得可靠的原始碼、技術文件或實機對照，請記錄來源、版本及具體證據。如果無法完全確認，必須標記為未確認，不可自行補出不存在的原廠行為。

### 這一階段的決策原則

先判斷原廠效果屬於哪一種：

**模型 A：離散飛彈模型**

每個電弧是獨立的投射物，具有自己的方向、速度、存活時間與動畫。

**模型 B：整體環形效果**

由一套整體幾何或光環效果控制外擴輪廓。

**模型 C：混合模型**

同時存在整體擴散控制和多個獨立動畫圖元。

實際模型必須由證據決定，不得事先指定。

如果原版本來就存在細小間隙，不應為了視覺上形成完美閉環而破壞原版行為。

如果專案另外要求提供平滑閉環的視覺模式，請將它設計成獨立模式，不要冒稱這就是原廠演算法。

## 五、第三階段：建立方向映射除錯工具

必須建立可以獨立測試方向的除錯畫面。

至少能夠：

* 逐一查看 16 個方向。
* 固定方向，逐幀播放 13 幀動畫。
* 隨時切換方向與影格。
* 顯示原始 DCC 方向索引。
* 顯示目前採用的世界方向。
* 顯示圖元的實際旋轉角度。
* 顯示 Pivot、Anchor、Offset 和圖元邊界。
* 同時查看原始影格與最終渲染結果。

請特別確認：

```text
World Direction
        ↓
Logical Direction
        ↓
DCC Direction Index
        ↓
Frame Selection
        ↓
Sprite Placement
        ↓
Final Rendering
```

每個步驟都必須可以追蹤。

### 禁止事項

不得直接假定：

```text
DCC Direction = atan2(y, x) 換算後的索引
```

也不得直接將原始圖元旋轉 45°、90° 或其他固定角度來掩蓋方向映射錯誤。

請先確認原始圖元本身的朝向，再決定是否需要旋轉。

如果目前的方向排序與標準角度不一致，請建立明確的方向查找表，而不是修改整個動畫系統中的角度公式。

## 六、第四階段：修復環形取樣與圖元間距

如果經確認，問題確實來自將獨立電弧排列成環形，請將環形幾何與動畫圖元分成兩個獨立模組。

```text
Nova Ring Geometry
        ↓
Placement Samples
        ↓
Direction Resolver
        ↓
Animation Frame
        ↓
Sprite Composer
        ↓
Blend / Rendering
```

### 6.1 不可以只用固定角度間隔

對螢幕上的橢圓而言，等角度間隔通常不等於等像素弧長間隔。

如果目前是：

```text
theta = i * 2π / N
x = centerX + radiusX * cos(theta)
y = centerY + radiusY * sin(theta)
```

請檢查這種等角度取樣是否造成部分區段的像素距離過大、其他區段則重疊。

但不得直接假定所有 Nova 場景都應該使用橢圓。必須由遊戲座標、投影方式與期望的畫面模型決定。

### 6.2 優先使用預計算的弧長查找表

若需要在螢幕橢圓上均勻排列圖元，優先考慮：

```text
Ellipse Geometry
       ↓
Precomputed Arc-Length LUT
       ↓
Equal-Distance Samples
       ↓
Sprite Positions
```

建構查找表時，可以離線或初始化時計算累積弧長，再利用插值查詢位置。

不要在每個圖元、每一幀都重複進行大量數值積分。

在半徑或長短軸比例改變時，必須正確更新取樣結果。

### 6.3 使用動態圖元數量

如果原廠行為允許使用離散圖元，並且目前的間距確實隨半徑增大而失控，可以考慮：

```text
Perimeter
    ↓
Desired Pixel Spacing
    ↓
Required Instance Count
    ↓
Evenly Spaced Samples
```

概念上：

```text
instanceCount = ceil(perimeter / targetSpacing)
```

其中 `perimeter` 必須代表目前實際渲染曲線的周長，不能直接使用未投影的世界座標圓周長。

如果為了效能使用上限，必須明確記錄最大圖元數量及其對最大間距的影響。

不得只固定使用 32、64 或其他任意數量，再期望所有半徑都能維持相同密度。

### 6.4 統一判斷間距

請實作除錯指標：

```text
Minimum Neighbor Distance
Average Neighbor Distance
Maximum Neighbor Distance
Maximum Visible Gap
Average Arc Spacing
Overlap Count
Instance Count
```

圖元的實際有效覆蓋寬度應以圖片的 Alpha／亮度分布測量，而不是直接把 72 × 50 的整格尺寸當成有效寬度。

若兩個圖元的矩形相交，不代表電弧像素一定接合；反之亦然。

## 七、第五階段：正確處理每個方向的圖元朝向

環形上的位置方向和圖元本身的繪圖朝向是兩個不同概念。

請分別計算：

```text
Sample Position
Radial Direction
Tangential Direction
DCC Direction
Final Sprite Rotation
```

不要把這幾種方向混為一談。

針對目前的 `electricnova.png`，請實際抽查 16 個方向的原始圖元，判斷電弧的主要延伸方向，以及是否存在不對稱的形狀變化。

至少製作兩種可切換的測試模式：

1. **原始方向模式**：依據資源方向映射直接選擇對應的原始影格。
2. **候選旋轉模式**：僅在有證據支持時，測試旋轉角度對方向排列的影響。

旋轉模式不得成為預設修復方式。

對每個候選方向計算：

```text
Requested Direction
Selected DCC Direction
Angular Difference
Sprite Long-Axis Direction
Placement Radial Direction
```

並在除錯畫面中顯示。

在通過連續性測試之前，不要將新映射套用到所有技能或共用方向系統。

## 八、第六階段：修復光帶厚度及混色

目前的問題可能來自圖元太薄、間距過大、方向錯誤或混色方式不對，不能一律透過多層疊加解決。

請先將問題分類：

```text
A. 圖元本身太薄
B. 相鄰圖元之間有空隙
C. 相鄰圖元互相重疊
D. 旋轉方向錯誤
E. Anchor / Offset 錯誤
F. 加法混色導致亮度過曝
G. 多層圖元的相位或半徑不一致
```

每一類都必須有獨立的診斷方式。

### 混色要求

如果現有透明圖層是使用黑色背景去背，請確認圖集實際 Alpha 通道與渲染器的混色策略一致。

不要因為背景看起來是黑色，就假定它是透明背景。

若採用加法混色：

* 檢查 RGB 與 Alpha 的實際計算方式。
* 避免重複套用 Alpha，導致能量效果不符合預期。
* 區分圖元密度不足與亮度過低。
* 不要用單純增加亮度來掩蓋黑縫。

### 多層光帶要求

只有在確認單層電弧本身無法滿足需求後，才允許測試額外光帶。

每層必須獨立配置：

```text
Radius
Thickness
Offset
Opacity / Intensity
Blend Mode
Animation Phase
```

半徑較小時必須避免所有圖層堆疊成白色圓餅；半徑較大時必須避免多層之間產生重影。

如有必要，採用隨半徑調整層距與厚度的方式，但必須以測試結果為依據。

## 九、第七階段：將幾何生成器與動畫 Builder 分離

不要將本次修復寫死在 `ElectricNova` 專用程式碼裡。

請在現有架構內建立或整理出下列職責：

```text
NovaEffectController
├── NovaGeometry
├── RingSampler
├── DirectionResolver
├── SpritePlacement
├── AnimationPlayer
├── LayerComposer
├── BlendController
└── NovaDebugOverlay
```

功能定義如下：

**NovaEffectController**

管理技能生命週期、擴散半徑、播放時間與結束條件。

**NovaGeometry**

計算目前效果的幾何形狀與投影座標。

**RingSampler**

依據選定的取樣策略產生位置，不負責解析 DCC。

**DirectionResolver**

將需求方向映射到正確的 DCC 方向，不直接改寫圖集。

**SpritePlacement**

根據 Anchor、Offset 和世界座標放置圖元。

**AnimationPlayer**

使用既有的標準動畫資料播放影格，不另寫一套 Nova 專用 Frame 播放器。

**LayerComposer**

依據已驗證的圖層設定組合畫面。

**BlendController**

統一執行混色策略。

**NovaDebugOverlay**

顯示位置、方向、影格、間距及錯誤指標。

上述名稱是架構目標，不是要求必須建立九個獨立檔案。如果現有專案已有對應模組，應優先重用。

## 十、第八階段：自動測試與視覺回歸

請建立自動化測試，至少包括以下項目。

### 方向測試

```text
✓ 16 個方向全部可以載入

✓ 相鄰方向不會無故跳轉

```

### 影格測試

```text
✓ 每方向 13 幀可正常載入
✓ 共 208 個方向／影格組合可索引
✓ Atlas 區域不越界
✓ Frame 播放順序正確
```

### 幾何測試

```text
✓ 取樣點數量符合當前策略
✓ 取樣沒有重複點
✓ 相鄰取樣距離落在設定容差內

✓ 半徑變大時不會無故大量出現空隙
✓ 不同長短軸比例都能穩定運作
```

### 混色測試

```text
✓ 透明背景正確

✓ 不會因為混色策略產生異常黑邊
✓ 重疊處不會無限制過曝
```

### 回歸測試

```text
✓ 原有動畫 Builder 仍然可用
```

測試結果不得只用「正常」或「已修復」帶過。必須列出實際數值、通過項目、失敗項目及尚未驗證項目。

## 十二、實作規則

1. 修改之前，先閱讀現有程式碼和資源格式。
2. 優先沿用既有 Standard Animation Template 和 Shared Builder。
3. 不要複製一套新的 DCC Decoder 或 Animation Player。
4. 不要為了修正 Nova 而破壞其他技能。
5. 不要以固定半徑、固定圖元數量或固定旋轉角度取代正確的幾何計算。
6. 未確認的原廠機制必須標記，不可當成已知事實。
7. 不允許用一張人工繪製的完整圓環取代原始動畫，除非另外建立明確的非原版視覺模式。
8. 不允許透過對每個圖元手動指定螢幕座標來掩蓋方向或 Offset 錯誤。
9. 如果現有架構已具備某項功能，先重用，不要再建立重複模組。
10. 如果測試發現問題源頭是 Atlas 解碼或 JSON 座標錯誤，必須先修正源頭，不要只修改渲染端。

## 最終驗收原則

我不要只是「看起來比較像圓」的修改。

我要先確認原廠資料的實際意義，再修正資源解碼、方向映射、幾何取樣、圖元間距、Anchor、Offset 或混色中真正出錯的地方。
