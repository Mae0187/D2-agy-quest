# 整體評價

這份文件的產品定位清楚，把「Agent 狀態 → D2 戰鬥場景」的映射講得很完整，工程邊界也抓得準，例如 25Hz 時鐘、2:1 等距、DCC 離散方向、加法混色。

不過有三個問題值得先處理：

1. 文件裡有幾個技術論述我認為不準確或過度肯定，若原樣放進給 AI 的 Prompt，會被當成事實放大。
2. 範圍可能過大：這是「監控看板」，不是 D2 模擬器。
3. 外部資源的角色分配應該調整：你本機的 MPQ 才是真理源，不是 Wiki。

---

## 一、建議查證或修正的技術論述

| 文件說法 | 問題 | 建議 |
|---|---|---|
| 直接用 `atan2(dy, dx)` 會有「30°~45° 嚴重偏差」 | 數學上最大誤差約 **19.5°**（`tanθ=√2` 時），不是 30~45° | 修正數字。結論（要做 `dy*2`）仍然正確 |
| Tile 寬 64px、高 32px | D2 地板 tile 是 5×5 subtile，約 160×80px，subtile 是 32×16px。64×32 是 2:1 比例沒錯，但不是 D2 的實際尺寸 | 公式只依賴 2:1 比例，所以不影響；但若要和原版地圖或碰撞對接，必須用原版尺寸 |
| 箭矢 DCC 有 135°/160° 基礎偏角、查表 `[4,0,5,1,6,2,7,3]` | 這些數字像是經驗值或記憶，缺乏來源。D2 投射物常見 1/8/16 方向，方向 0 對應世界座標的固定方向，並非每張圖各有任意偏角 | **不要寫死**，改成每個 missile 的資料欄位（`dirCount`、`dir0WorldAngle`、`clockwise`），並用校準工具實測 |
| `FPS = 25 * AnimationSpeed / 256` | 概念大致對，但速度與「動作判定幀」來源主要是 **AnimData.D2 / COF**，不是 Skills.txt。文件把 Skills.txt 寫成含判定幀，容易誤導 | 判定幀、速度從 AnimData.D2 與 COF 讀，Skills.txt 只提供動作代號與回呼函式 |
| 「Trans=1 或 2 都是加法混色」 | D2 有多種混色模式（一般、25%/50%/75% alpha、加法、亮度等），不是一律 `lighter` | 實作 `blendMode` 列舉，不要只做 `'lighter'` |
| 各職業幀數（德魯伊待命 6 幀等） | 若來自記憶，風險很高 | 一律從實際 DCC / COF / AnimData 動態讀取，不要手寫常數 |
| 「資料驅動狀態機就能涵蓋 210 技能」 | D2 的投射物與技能行為大量依賴 **硬編碼函式**（Missiles.txt 的 `CltDoFunc`、`SrvDoFunc`、`CltHitFunc`，Skills.txt 的 `srvdofunc` 等），不是純資料 | 需要「行為原語庫」（約數十種）加資料參數，見下文 |
| 抖動／走路不連續只歸因於幀率 | 還可能是 COF 各圖層幀數不一致、各幀錨點偏移（offset）漂移，以及位移速度與動畫週期不匹配造成的**滑步（foot sliding）** | 增加「圖層幀數一致性檢查」與「每週期位移距離校驗」 |

另外，文件說的「所有精靈圖 Index 0 純透明」只解決一部分黑邊問題。更常見的原因是：本該加法混色的特效被用普通 alpha 繪製，或 PNG 做了 premultiplied alpha 錯誤處理。

## 二、策略層建議：控制範圍

1. **看板不需要完整模擬 D2。**
   - 只需要視覺還原，不需要傷害、抗性、仇恨等伺服器端邏輯（`SrvDmgFunc`、抗性衰減）。
   - 文件把 Diablo Archive 當「戰鬥導演邏輯真理源」，但導演只要「好看且有節奏」，不必數值正確。

2. **210 技能不要平均用力，改為三級分層：**
   - **A 級（約 20~30 個）**：直接對應 Agent 狀態的招牌技能，手工打磨。
   - **B 級**：依行為家族歸類（直線投射、追蹤、地面範圍、環形新星、持續光束、召喚、光環等，約 15~20 個家族），每個家族寫一次行為，技能只填參數。
   - **C 級**：只做「換皮」，共用家族行為加不同貼圖與調色。

3. **真理源順序應調整：**
   - 第一順位：本機 MPQ 的 `MonStats.txt`、`MonAI.txt`、`Skills.txt`、`Missiles.txt`、`Overlay.txt`、`MonSounds.txt`、`SuperUniques.txt`。這些是原廠數據，比 Fandom Wiki 準確。
   - Wiki 只做交叉驗證。
   - **Spriters Resource 當 Boss 本體來源要小心**：它的圖多半也來自 MPQ，但已經被裁切、重排，通常**丟失原始偏移錨點、調色盤資訊、方向編排**，反而增加對齊成本。你既然已有 DCC 解碼管線，建議 Boss 也直接從 MPQ 出，Spriters Resource 僅作比對。
   - 素材僅限本機私用，不要公開散布暴雪資產。

## 三、架構建議

### 1. 時鐘與渲染分離
- 邏輯 25Hz 固定步長，渲染用 rAF 並對位置做插值（alpha = accumulator / 40ms）。
- 動畫幀仍按原版速度步進，位置插值可以讓 60/144Hz 螢幕上位移更順，而不改變原版手感。
- 視窗隱藏或失焦時降頻到 5~10Hz 或暫停。作為常駐懸浮層，**CPU/電量**是產品體驗的一部分。

### 2. 方向系統：做成「校準」而非「推算」
```ts
interface DirectionSpec {
  dirCount: 1 | 8 | 16 | 32;
  dir0WorldAngle: number;   // 實測得出
  clockwise: boolean;
  rotationMode: 'discrete' | 'none' | 'free'; // AlwaysRot 之類
}

// 螢幕 → 世界平面角（修正 2:1）
const worldAngle = Math.atan2(dy * 2, dx);
// 世界平面速度 → 螢幕速度
const sx = v * Math.cos(worldAngle);
const sy = v * Math.sin(worldAngle) * 0.5;
```
並建議做一個 **「方向校準頁」**：每個 missile 以 0~360° 每 5° 發射一次，疊加理論方向箭頭與實際貼圖，一眼看出錯位，再把結果寫入資料。這比任何 AI 給的查表矩陣都可靠。

### 3. 行為原語庫加資料參數
把 `Missiles.txt` 的 do/hit function 對應成 TypeScript 行為模組，例如 `Linear`、`Homing`、`Spiral`、`Random`、`Nova`、`Beam`、`Summon`、`GroundPersistent`。技能管線只組合這些原語與參數，這才是可擴展的「資料驅動」。

### 4. 記憶體：用調色盤索引，而非 RGBA 解碼
- 若走 WebGL，可以把精靈存成 **8-bit 索引圖加調色盤查找紋理**，記憶體約降到 1/4。
- 同時天然支援 D2 的調色盤換色（冰凍、中毒、精英變色）與加法混色，不必預烘焙多份 PNG。
- 若維持 Canvas2D，至少做 atlas 打包、`ImageBitmap`、LRU 與引用計數，以及在 Worker 或 OffscreenCanvas 中解碼，避免主執行緒卡頓。
- 300MB 目標要先量測：統計「單技能平均像素量 × 同屏併發數」，再決定快取上限。

### 5. 先做「除錯可視化」
疊加層可切換顯示：方向索引、碰撞框、判定幀觸發點、錨點、當前幀與總幀、混色模式。沒有這個，210 個技能的驗收會非常痛苦。

## 四、對 Prompt Spec 的改進建議

現版 Prompt 的主要弱點：

- **沒有提供真實資料樣本**：AI 沒看到你的 Manifest 結構、Missiles.txt 幾行、現有程式碼技術棧（Canvas2D？WebGL？TS？框架？），只能憑空設計，最後會與你現有碼不相容。
- **把未驗證的數值當事實寫入**（135°/160°、查表矩陣、30~45° 等）。
- **一次要求四大模組**，輸出會淺。
- **缺少驗收條件與輸出格式**。
- **沒要求 AI 標示假設與不確定處**，容易幻覺 D2 細節。

建議改成分段提問，每段附上：

```markdown
## 背景（精簡）
...（保留你現有的約束 1~5，但把未驗證數值標為「待校準參數」）

## 我提供的真實資料
- Manifest 單筆範例（JSON，3~5 筆）
- Missiles.txt 表頭 + 5 列（火球、箭、骨矛、冰封球、閃電）
- 現有 Sprite/Animation 控制器的介面（TypeScript）
- 技術棧與瀏覽器目標

## 本次只處理：【模組二：投射物引擎】
## 輸出要求
1. TypeScript 介面與可運行的核心函式
2. JSON Schema（含校驗規則）
3. 至少 10 組「輸入角度 → 預期方向索引與螢幕速度」測試向量
4. 明確列出：你做了哪些假設、哪些 D2 細節你不確定
5. 不要使用 CSS rotate 或固定 60FPS tween
## 禁止
- 憑記憶編造 D2 的具體數值；不確定就標為參數
```

另外，第六章的「絕對會更快」建議改成「能更快產出骨架，但數值與方向仍需本機校準」。

## 五、Roadmap 調整

在原本里程碑前面，增加一個基礎里程碑：

- **里程碑 0：基礎設施與除錯工具**（建議先做）
  - 統一時鐘（固定步長加插值）與 AnimData/COF 驅動的幀速、判定幀。
  - 動畫圖層幀數一致性與錨點漂移檢查（直接針對德魯伊抖動、聖騎士不連續）。
  - 方向校準頁與技能展示廊（Skill Gallery，可 360° 掃射）。
  - 混色模式列舉與黑邊檢測。

之後的調整：

- **里程碑 1（投射物方向）**：驗收標準從「100% 精準」改成可量測：與理論方向誤差小於半個離散格（8 方向 22.5°、16 方向 11.25°），並由校準頁自動出報告。
- **里程碑 2**：先實作 4~5 個行為家族，再選招牌技能，而不是先挑技能。
- **里程碑 3（Boss）**：建議順序為 **安達利爾（環形新星）→ 迪亞布羅（光束加火環）→ 巴爾 → 督瑞爾 → 墨菲斯托**，由簡到繁。迪亞布羅的光束其實可以重用你的「持續光束」家族。
- **里程碑 4**：新增「Agent 事件到技能預設」的映射層（例如 `TOOL_RUNNING` 隨機抽 A 級技能），讓看板的主要價值（狀態可讀性）早一點上線，而不是等 210 技能全部完成。

## 六、最優先可做的三件事

1. 做**方向校準頁**，把方向與偏角從「猜」變成「量」。
2. 做**幀速與圖層一致性檢查器**，用資料解釋德魯伊抖動與聖騎士不連續，而不是靠體感調。
3. 把 **210 技能依行為家族分群**（先用 Missiles.txt 的 do function 與 Skills.txt 的 srvdofunc 做自動分組），算出實際要寫的行為數量。這個數字通常比 210 小一個數量級，也能讓你更準確估算工期。

如果你願意，我可以幫你做其中一項：例如產出「行為家族分類表」的草案，或把 Prompt 改寫成可直接貼給 AI 的分段版本。
