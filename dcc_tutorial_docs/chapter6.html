6.1 About Multi-part Animations

When dealing with some monsters, you'll surely encounter some strange configurations. Take for example the Fallen Token (FA). If you look at it, you'll see that it's composed of 6 parts.

Each part holds the animations for a body part (arm,torso etc ...) or some kind of overlay. If you want to replace this Token, you'll have to change some of this parts with your animations but what will you do with the others ... You can't let the arms or shield of the original animation be displayed over your new superb Monsters !

The solution : Invisible DCC.

Before changing a multi-part animation, you have to find the sub-token that holds the needed modes (A1, A2 etc ...) and note down which subtokens are unused. In our example, you'll see that the core animations are displayed in the TR subtoken and that the subtokens SH,S1 and RH have to be "cancelled". Take for example this part of the SH subtoken :

So following the first part of the tutorials, you are now able to change the contents of the TR folder. Do so and head up to next step ...

After completing this part, you still need to cancel the other subtokens. Take this file, it contains a set of dcc files with 8, 16 and 32 directions, and 255 frames per direction. If you open it, you'll see that each frame is 1x1 pixel with transparency. It could be used to replace any dcc you want to cancel. Note down the dcc name of the files you want to cancel, copy the void.dcc to the forementioned folder, duplicate it and rename it.

Now launch Diablo II, head to your monster and it should be fine.

6.2 The eComponent < NUM_COMPONENTS Assertion Failure:

If after giving a monster new animations the game crashes with this assertion message:

Assertion Failure
Location : C:\Projects\Diablo2\Source\D2Client\Engine\GfxUtil.cpp, line #1352
Expression : eComponent < NUM_COMPONENTS

that means the .COF and .D2 editing of the framecounts has an error somewhere. Refer to Chapter 5 of this tutorial for a thorough explanation of the process. Make sure you edited both the .COF and animdata.d2, and that you correcly placed in the data\global folder the .d2 files that can be downloaded here. If you don't, your .COF modifications won't work.

6.3 The (UINT)nAnimFrame <= tCelContext.dwCelsPerDirection Assertion Failure - Animation Sequences:

So, you gave a monster token fresh new graphics, and all seems to be working good; but, all of the sudden, the game crashes with this assertion message:

Assertion Failure
Location : C:\Projects\Diablo2\Source\D2Client\UNIT\CUnit.cpp, line #1436
Expression : (UINT)nAnimFrame <= tCelContext.dwCelsPerDirection

This error is related to an animation sequence. Let's now take a look at animation sequences, and how to solve the error above:

6.3.1 What are animation sequences, and how to work with them :

We saw before that there are .dcc files corresponding to the animation modes, like attack, walk, neutral and so on. But if we take those little flayers that appear in the act 3 jungles for example, you will see that there is no .dcc file with the animation of these flayers being revived. Still, they do rise from their remains in the game. Where is this animation then, if it is not together with the other animations?

Actually, it is there. If you look closely, you will see that the reviving animation for the flayer is exactly the same as their death animation, only played backwards!!

The reviving animation of the flayer is an example of an animation sequence. In more precise words now: an animation sequence for a monster is a sequence of certain specific frames taken from the existing dcc files, in a certain specific order. There is a table in d2common.dll that contain the information on all animation sequences the D2 monsters use; there are 57 monster animation sequences in total.

You can check what animation sequences the monster you are working with uses, if it uses any. To do so, open monstats.txt, and search for the monster you want. Now, look for the columns called Skill1Seq, Skill2Seq, Skill3Seq, Skill4Seq, Skill5Seq. The numbers in these columns indicate what animation sequences the skills performed by the monster use. In our Flayer example, you will notice that Skill1, 158, uses animation sequence 32. Skill 158 is Skeleton Raise (you can check this in skills.txt), the skill used among other things to revive Flayers. So, 32 is the number of the animation sequence displayed when a flayer is being revived.

Sometimes, the skill sequence used to perform a certain skill could be replaced by an animation mode without problems; for instance, certain attack animation sequences could be replaced with the attack1 animation mode. If you do so (and I will explain how in a second), the game will use the attack1 dcc instead of building an animation sequence for the skill. If the monster that is crashing on you uses an animation sequence that is visually replaceable by an animation mode dcc (check skills.txt to determine what skill is using an animation sequence like I exemplified above), I suggest you do so, as it is an easy fix. Here's how to solve it:

First, get in monstats.txt the ID of the monster skill that is crashing on you, in the Skill1, Skill2, Skill3, Skill4, or Skill5 column. Now, open skills.txt, and go to the skill you need to change. For this skill, you have to modify the values in two columns, anim and monanim:

  • Change the value of the anim column to seq;
  • Change the value of the monanim column to one of the following: a1, a2, sk1, sk2, sk3, sk4, depending on the animation mode you want to use for this skill. Note this must be a valid animation mode, don't try to put a2 here if the monster does not have an attack2 animation for example.

The modifications above should solve your problem with the game crashing.

Sometimes, however, there is no existing animation mode that would look good for the skill that is crashing on you (for example, the reviving animation sequence). It is in those cases that you will have to open a hex-editor and work in d2common.dll.

In the rest of this discussion on animation sequences, we will see what is causing the error above, and how to solve it by editing the animation sequences directly in d2common.dll.

I will explain the meaning of all this with the bytes of Frame number 8, the one highlighted in the table above. As you can see, the 16 bytes for each frame are actually 4 sets of 4 bytes each. I marked them with different colors as usual, and here's what they do:

  • The blue bytes tell the game the animation mode from where this frame is going to come from; in the case of frame 8, the bytes are 04 00 00 00. That means frame number 8 will come from the Attack1 animation mode. To know what number goes with which animation mode, check the list below:

    • Animation ModeNumber

    Neutral01
    Walk02
    GetHit03

    Skill30A

    Corpse0C
    Knockback0D
    Sequence0E
    Run0F

  • The green bytes tell the game the direction of the animation mode (defined by the blue bytes), from which the frame is to be taken. If you find 00 00 00 00 here, that means the direction to be defined is the one that is being currently displayed on screen. For example, if a Sand Leaper is facing down in the game screen while you're playing, and leaps at your character, the frame number 8 of the leap animation sequence is going to be taken from the down direction (the current direction) of the attack1 animation mode.
  • The orange bytes tell the game what frame is to be taken from the animation mode defined by the blue bytes, and from the direction defined by the green bytes, and used as the frame for the animation sequence. In our example we have 07 00 00 00 here, that means the frame number 8 of the leap animation sequence is the frame number 08 of the current direction displayed, of the attack1 animation mode (and YES, that is frame number 08 and not 07; frames are internally counted starting from 00 by the game, so the first frame is actually 00 and NOT 01. Don't forget this! );
  • The violet bytes contain event information. They tell the game is an event is to take place in this frame. 02 00 00 00 is the missile event; this way, the game knows it has to display on screen a certain missile (defined elsewhere) when frame 8 is displayed. The possible events are:

    NumberEvent
    00No Event
    01Attack
    02Missile
    03Sound
    04Skill

That is pretty much it! Now, to 2 practical examples showing how to edit correctly an animation sequence:

Example 1: sequence number 13. It uses 20 frames of the sand leaper's attack1 animation, as we saw before. The original attack1 animation of the SL token has 160 frames; but, let's say your new attack1 animation for this token has 120 frames, what to do?

120 frames is 15 frames per direction, which means the leap animation sequence will certainly crash when it tries to get frames 16, 17, 18, 19, and 20 of the attack1 animation's current directions, since there are no such frames anymore. To fix that, you will have to disable those frame entries. To do that, check the first table for the offset of the 13th animation sequence, an go to that offset using the hex-editor. You will see this:

20 F7 DC 6F 14 00 00 00 14 00 00 00

We want to disable the last 5 frames, and let this be an animation sequence that uses only the 15 frames per direction of the attack1 animation. In this example that's easy, simply change the red and white bytes from 14 to 0F, like this:

20 F7 DC 6F 0F 00 00 00 0F 00 00 00

If you remember what I explained before on the red and white bytes in here, this will simply tell the game that this animation sequence has a total of 15 frames per direction, and as a consequence the game will ignore the information that is originally there on frames 16, 17, 18, 19, and 20. NOTE: Do NOT delete the information on those frames. If you delete them, you will screw up the structure of the pointers in d2common.dll, and the game will most likely crash on you.
